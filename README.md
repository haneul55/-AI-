## 왜 어려운가: 데이터에서 찾은 것

- **한글명은 영문명을 소리 나는 대로 적은 것입니다.** `모닝쿠리어 → Morning Courier`, `글로비스 세이프티 → Glovis Safety`, `제7하나 → No. 7 Hana`, `아세안 캡틴 → Asian Captain`. 카탈로그에는 한글이 **0%**라 글자 비교가 통하지 않습니다.
- **한글 기록은 train의 9.7%(1,191행 / 고유 382척)뿐인데 평가 가중치는 70%입니다.** 즉 소수 집단이 점수의 대부분을 결정합니다.
- **한글명과 정답 카탈로그명의 정규화 편집유사도는 평균 0.010입니다.** 사실상 무작위 수준입니다. 반면 비한글은 88.4%가 편집거리 2 이내입니다.
- **영문명 완전일치율은 58.3%뿐입니다.** 나머지 41.7%는 1~2글자 오타(글자 교환·누락·중복)입니다.
- **톤수는 97.7%가 상대오차 5% 이내입니다.** 신뢰할 수 있습니다. 다만 **톤수만으로는 후보가 평균 1,228척**이라 단독 결정 근거가 될 수 없습니다.
- **국적·선종은 기록이 한글, 카탈로그가 영문이고 다대다입니다.** `파나마 → Panama`가 79.6%일 뿐 나머지 20%는 다른 국적으로 갈립니다.
- **`call_sign`은 선박 신원의 결정론적 식별자입니다.** train 안에서 5,851개 고유값이 정답과 1:1이고, 한 값이 두 선박을 가리키는 경우는 0건입니다.
- **그리고 전부 행 단위로 계산됩니다.** 전역 분포를 쓰지 않으므로 행 독립성 규칙을 구조적으로 만족합니다.

## 접근 방법

```mermaid
flowchart LR
	Q["입출항 기록 1행"] --> V["이름을 3개 표현으로 투영<br>raw · roman · phon"]
	V --> B["후보 생성 (blocking)<br>표현별 상위 K 합집합<br>78,595 → 482척"]
	B --> F["쌍 특징 44개<br>이름 유사도 13 · 구조 12<br>제원 정합성 12 · 식별자·순위 7"]
	F --> R["LightGBM lambdarank<br>후보 순위 재정렬<br>ndcg@1 최적화"]
	R --> O["질의별 1위<br>vessel_id"]
```

1. **표현 투영(`text.py`)**: 이름을 `raw`(영숫자 원문) · `roman`(자모 로마자) · `phon`(음소 정규화) 세 가지로 봅니다. `phon`이 핵심입니다.
2. **후보 생성(`index.py`)**: 표현별 상위 K의 **합집합**에 `call_sign` 조회 결과를 **강제 포함**합니다. 정답이 후보에 없으면 이후 단계에서 복구할 수 없으므로 재현율이 전부입니다.
3. **특징 44개(`features.py`)**: 이름 유사도(Levenshtein·Jaro-Winkler·token_set·partial), 이름 구조(길이·머리글자·숫자·토큰 겹침), 제원 정합성(세 톤수 정의별 상대오차·선종·국적 조건부확률), 식별자·순위(조회 적중·후보 내 순위·후보 수).
4. **순위 재정렬(`ranker.py`)**: `lambdarank`, `ndcg@1` 최적화. 정답은 후보 안에 최대 하나뿐이므로 분류가 아니라 순위 문제입니다.
5. **행 독립성(`pipeline.py`)**: `call_sign` 조회표는 `train.csv`만으로 만들고 `model/`에 동결합니다. 교차검증에서도 자기 fold를 제외한 나머지로 만들어 평가 조건을 정확히 재현합니다.

### 핵심 아이디어: 음소 정규화

한글을 영문으로 **되돌리는** 것이 아니라, 양쪽을 **같은 음소 공간으로 옮깁니다**.

```
초성   ㄱㄲ→K  ㄴ→N  ㄷㄸ→T  ㄹ→L  ㅁ→M  ㅂㅃ→P  ㅅㅆ→S  ㅇ→묵음  ㅈㅉㅊ→C  ㅋ→K  ㅌ→T  ㅍ→P  ㅎ→H
중성   ㅏ→A  ㅓㅗ→O  ㅜ→U  ㅣ→I  ㅔㅖ→E  ㅡ→삭제
종성   ㄱㄲㅋ→K  ㄴㄵㄶ→N  ㄷㅅㅆㅈㅊㅌ→T  ㄹ→L  ㅁ→M  ㅂㅍㅄ→P  ㅇ→NG  ㅎ→H
영문   PH→P TH→T SH→S CH→C CK→K QU→K X→KS  /  B·F·V→P  G·C·Q→K  D→T  R→L  Z→S  J→C  /  중복 자음 축약
```

두 가지 설계 판단이 성능을 갈랐습니다.

- **파열음의 유·무성 대립을 합칩니다.** `G/K`, `B/P`, `F/P`, `D/T` 구분은 한글 음차에서 일관되지 않습니다. 합치는 쪽이 유리했습니다.
- **`ㅡ`를 삭제합니다.** `글로비스`의 `ㅡ`는 자음충돌 방지용 삽입모음이지 발음이 아닙니다. 버려야 `GLOVIS`와 만납니다.

```
글로비스 세이프티 → KLLOPISSEIPTI     Glovis Safety  → KLOPISAPETY    (겹ㄹ 하나 차이)
뉴콘크          → NYUKONK           New Konk       → NEWKONK
펭슈하이         → PENGSYUHAI        Feng Xiu Hai   → PENKSIUHAI
```

### 검증 결과

| 검증 설정 | 가중 | 한글 | 비한글 |
| --- | --- | --- | --- |
| 이름 유사도 단독 (베이스라인) | 0.7058 | 0.5928 | 0.9694 |
| 선박 단위 분할 · 이름+제원만 (**최악**) | 0.9409 | 0.9160 | 0.9990 |
| 행 분할 · 이름+제원만 | 0.9745 | 0.9639 | 0.9991 |
| **행 분할 · call_sign 이력 포함 (제출 번들)** | **0.9933** | **0.9908** | **0.9993** |

- **행 분할** = 무작위 행 분할. 실제 평가 데이터(3,000행)와 조건이 같습니다.
- **선박 단위 분할** = 학습에서 본 적 없는 선박만 평가에 등장하는 최악 조건입니다. 이 0.9409와 0.9933의 **간격이 곧 일반화 비용**입니다.
- 후보 생성 재현율 **0.9993**, 후보 중앙값 **482척**.

### 버그와 교훈

테스트 45개가 실제 버그 4건을 잡았습니다. 포트폴리오 관점에서 가장 값진 기록입니다.

| 버그 | 증상 | 원인 | 영향 |
| --- | --- | --- | --- |
| 자모 분해 반환값 불일치 | 즉시 크래시 | 비한글 경로가 2-튜플, 한글 경로가 4-튜플 | 실행 불가 |
| 중성 인덱스 falsy 판정 | `라온` → `LAON` (r이어야) | `ㅏ`가 중성 인덱스 **0**이라 `if jung`이 거짓 | 한글 top-1 0.500 → 0.508 |
| 순차 전역 치환 | `CHAMPION` → `KAMPION` | `CH→C`로 만든 `C`를 뒤의 `C→K`가 덮어씀 | 한글 top-1 0.589 → 0.618 손실 |
| 후보 전량 선택 시 정렬 생략 | 후보가 카탈로그 앞쪽에만 몰림 | `k ≥ n`일 때 `argsort`를 건너뜀 | 데모 데이터에서 재현율 0.30 (실데이터 미발현) |

교훈: **측정하지 않은 것을 최적화하지 말 것.** 텍스트 엔진 수정만으로 이름 단독 베이스라인이 0.6949 → 0.7058로 올랐고, 한글은 0.5785 → 0.5928이 됐습니다. 이 차이는 랭커가 아니라 **표현 계층**에서 나온 것입니다.

| K=300 · 한글 2배 | 545 | 0.9954 | — |
| K=300 · 한글 4배 | 661 | **0.9961** | — |
| K=300 · 한글 6배 | 775 | 0.9971 | — |
| 톤수 ±5%만 (비교군) | 1,139 | 0.895 | 0.709 |
| 톤수 ±20% + 국적 (비교군) | 216 | 0.778 | 0.657 |
| 톤수 ±20% + 선종 + 국적 (비교군) | 31 | 0.584 | 0.529 |

한글 4배 확대는 평균 후보쌍을 487 → 661로만 늘리면서 재현율을 0.9387 → 0.9647로 올립니다. 반면 제원 필터는 후보를 극적으로 줄이지만 **정답을 함께 버립니다.**

## 리더보드 분석

이 파이프라인의 리더보드 점수는 아직 없습니다. 다만 남은 개선 여지를 정량화하면 다음과 같습니다.

- 한글 기록은 300행으로 추정되며 가중치 0.7 → **한글 1행 ≈ 0.00233점**
- 비한글은 2,700행 가중치 0.3 → **비한글 1행 ≈ 0.00011점**
- 즉 **한글 1행이 비한글 21행과 같습니다.** 비한글은 이미 0.9993이라 남은 점수는 사실상 한글에만 있습니다.
- 교차검증 기준 한글 오답은 11행(0.9908)입니다. 이 11행을 절반으로 줄이면 +0.0128입니다.

## 다음 개발 방향 (한글 집중)

1. **동명 선박 대응**: 이름 특징이 만점 동점이 되면 제원에만 의존합니다. 후보 간 pairwise 비교 특징을 추가합니다.
2. **학습 기반 음차 복원**: 현재 규칙은 수작업이라 중국어·일본어 음차에 약합니다(`펭슈하이 → Feng Xiu Hai` 유사도 0.71). seq2seq로 대체합니다.
3. **한글 자모 단위 오타 증강**: 지금 학습 데이터는 실제 분포를 그대로 씁니다. 받침·모음이 바뀐 표기 변형을 증강합니다.
4. **후보 top-5 + 근거 특징 출력**: 실무 수용성을 위해 정답 하나가 아니라 후보와 근거를 함께 제시합니다.
5. **시드 앙상블**: 랭커 시드를 바꿔 2~3개를 평균합니다.
6. **후보 K 확대**: 서버 여유(추론 20분 대비 1분)를 활용해 K=500까지 올려 후보 재현율 상한을 올립니다.

## 제출 규격 준수

| 규칙 | 대응 |
| --- | --- |
| 추가 데이터 금지 | `train.csv` + `vessel_catalog.csv`만 사용. 외부 사전학습 가중치·임베딩 미사용 |
| **평가 행 독립** | 한 행의 예측은 그 행의 입력 + 카탈로그 + `model/`에 동결된 조회표로만 결정 |
| 동일 행 재실행 동일 결과 | blocking·특징·랭커 모두 행 단위 독립. 순서·부분집합 무관 (테스트로 검증) |
| 데이터 유출 금지 | 평가 데이터를 로그·파일로 내보내지 않음 |
| 제출 구조 | `submit.zip` 최상위에 `model/`, `script.py`, `requirements.txt` **정확히 3개** |
| 인터넷 불필요 | 모든 패키지가 평가 서버 기본 설치본. 추론 중 외부 다운로드 없음 |
| 실행 시간 | 200행 15.7초 (제한 20분) |

`script.py`는 `scripts/make_submit.py`가 `src/vesselmatch/`의 모듈들을 의존성 순서대로 **자동으로 합쳐** 생성합니다. 제출물이 항상 소스에서 파생되므로 "제출 코드와 저장소 코드가 다르다"는 사고가 원천적으로 막힙니다.

## 실행 방법

```bash
pip install -r requirements.txt

# 대회 데이터를 data/ 에 배치 (재배포 금지)
# 또는 합성 데이터로 동작 확인
python scripts/make_demo_data.py --out data_demo

# 학습 + 5-fold 교차검증 (전체 약 13분, CPU)
python scripts/train.py

# 빠른 확인 (표본 3,000행)
python scripts/train.py --no-cv --sample 3000 --out model/bundle_quick.pkl

# 최악 조건 검증
python scripts/train.py --split group --use-call-sign 0

# 제출물 생성
python scripts/make_submit.py --zip

# 테스트
python -m pytest tests/ -q
```

GPU는 필요 없습니다. 평가 서버 사양(L4, 26GB RAM)에 크게 여유가 있습니다.
